# 链路图 · 「认养下单」全链路（含行号）

> 产出日：2026-11-08（D1）　作者：一季一鲜测试工程
> 目的：**不看代码**也能讲清"用户在商品页点认养后发生了什么"，并能说出每一步在哪个文件哪一行。
> 图例：`[FE]` 前端　`[BE]` 后端　`[DB]` SQLite
> ⚠️ 本文档 11-08 修订过一次：初版误判「前端没接后端」，实际是 **漏看了 `js/api.js`**。现结论已逐条复核。

## 0. 一句话结论（先记住这句）

> **一季一鲜 = 前端静态数据 + 后端真接口，两者用 `js/api.js` 接通了大半。**
> 前端有一层完整封装 `js/api.js`（15 个端点、token 管理、统一错误处理），被 6 个页面引用；
> **唯一还没接后端的是"商品列表页" `products.html`**——它直接用 `data.js` 的本地常量，
> 代码注释里写着「上线后替换为 `fetch('/api/products')`」。

→ 这不是 bug，是我们**接下来 15 天的改造清单之一**（见 §4）。

## 2. 用户侧动作 → 代码落点（主链路）

### 2.1 商品列表（`products.html`）—— ⚠️ 唯一没接后端的页面

| 步 | 发生了什么 | 落点 |
|---|---|---|
| 1 | `<script src="data.js">` 把商品常量注入页面 | `products.html` head |
| 2 | `const mockProducts = PRODUCTS;` —— **用本地常量当数据源** | `products.html:416` |
| 3 | `getFiltered()` 按 region / zone / cat / 搜索词过滤 | `products.html:529` |
| 4 | `pickNine()` 每次取 9 个，`renderProducts()` 渲染卡片 | `products.html:557 / 713` |
| 5 | 卡片按钮文案是**「查看详情」**，点击跳 `product-detail.html?id=xxx` | `products.html:592-595` |

> 📌 `:414` 那行 `fetch('/api/products')` **出现在注释里**（「上线后替换为 fetch('/api/products')」），
> 真代码在 `:416` 直接把数据源定死成 `mockProducts`。
> → **数据是静态的**。如果后端改了价格 / 库存，列表页不会变。

### 2.2 商品详情 + 下单（`product-detail.html`）—— ✅ 真调后端

| 步 | 发生了什么 | 落点 |
|---|---|---|
| 1 | 从 URL 取 `?id=`，从 `PRODUCTS` 里 find 出商品（**详情页商品数据也是静态的**） | `product-detail.html` |
| 2 | 页面引 `js/api.js`；用 `AuthAPI.isLoggedIn()` 判断登录态 | 页面脚本 |
| 3 | 「立即认养」→ **未登录则跳注册**（`AuthAPI`） | — |
| 4 | 填收货信息 → `UserAPI.getAddress()` 读默认地址 | `product-detail.html` |
| 5 | **提交下单**：`await OrderAPI.create({...})` | **`product-detail.html:950`** |
| 6 | `js/api.js` → `request('/orders', {method:'POST', body})` → 加 `Authorization: Bearer <token>` | `js/api.js` |
| 7 | → `POST http://localhost:3001/api/orders` | **后端 `server.js:303`** |
| 8 | 成功后弹 toast / 跳个人中心 | `product-detail.html` |

> 📌 另外两处也会下单：`js/farm-detail.js:2436`（认养农场）、`js/wholesale-detail.js:1683 / 1731`（批发）。

### 2.3 后端下单接口（`POST /api/orders`）

`backend/server.js`：

| 步 | 发生了什么 | 落点 | ⚠️ 缺陷 |
|---|---|---|---|
| 1 | 鉴权：没有 `Authorization: Bearer <token>` 直接 401 | `server.js:303` → `authMiddleware` `server.js:33` | — |
| 2 | 取参 `product_id / quantity / receiver_name / receiver_phone / receiver_address` | `server.js:305` | **quantity 无正整数校验** |
| 3 | 收货三要素非空校验 | `server.js:310` | 手机号不校验格式 |
| 4 | `SELECT * FROM products WHERE id=?` 读商品 | `server.js:316` | — |
| 5 | `if (product.stock < quantity) 库存不足` | `server.js:329` | **读-判-写非原子**（无事务） |
| 6 | 查同用户同商品是否已有 `pending` 单 → 有则**累加数量** | `server.js:334` / `345` | 无购物车，只能靠重复提交累加 |
| 7 | `INSERT INTO orders ...` 或 `UPDATE orders SET quantity=?` | `server.js:347` / `371` | — |
| 8 | `UPDATE products SET stock = stock - ?` | `server.js:377` / `381` | **未 await，且无事务 → 并发超卖** |
| 9 | 返回 `total_price: product.price`（**单价**，且是 TEXT） | `server.js:387` | **金额不守恒** |

### 2.4 订单列表与取消（`profile.html`）

| 动作 | 前端 | 后端 |
|---|---|---|
| 看我的订单 | `profile.html:865 / 1726` → `OrderAPI.list()` | `GET /api/orders` `server.js:396` |
| 取消订单 | `profile.html:1089` → `OrderAPI.cancel(id)` | `PATCH /api/orders/:id/cancel` `server.js:416` |

取消接口内部：`SELECT * FROM orders WHERE id=? AND user_id=?` → **归属校验在这，横向越权走不通**（`server.js:420`）
→ 状态必须 `pending`（`server.js:430`）→ `UPDATE orders SET status='cancelled'` + `UPDATE products SET stock = stock + order.quantity`（`server.js:437-438`）

> 📌 缺陷 #1 的"回旋镖"：若订单 quantity 是 -5，取消时 `stock + (-5)` 会让库存**再减 5**。即"下单 +5、取消 -5"双向污染。

### 2.5 其余已接通的接口（`js/api.js` 实际请求的端点）

```
/auth/register   /auth/login   /auth/me
/products?{qs}   /products/{id}
/orders          /orders/{orderId}/cancel
/favorites       /favorites/count   /favorites/{productId}   /favorites/check/{productId}
/farmer-follows  /farmer-follows/{farmerId}   /farmer-follows/check/{farmerId}
/user/address    /user/location
```
外加 `map.html:257` 直连 `/api/viz/stats`。

> 后端 24 条路由里，前端**用到约 15 条**。未使用的有：`/api/viz/stats` 之外的统计类、
> `PUT /api/user/address` 的部分分支等 → 详见 `docs/接口清单.md`（D2 产出）。

### 2.6 数据从哪来（前后端共用同一个文件）

```
data.js:14   const PRODUCTS = [ ...267 条... ]
     │
     ├──[FE] products.html / product-detail.html 直接读这个常量
     │
     └──[BE] backend/server.js:639  initProducts()
             ├─ 正则从 data.js 抠出 `const PRODUCTS = [...]`   (server.js:659)
             ├─ `new Function(...)` eval 出对象数组              (server.js:665)
             └─ 逐条 INSERT 进 SQLite products 表             (server.js:675)
```

> **前后端是同一份数据的两个副本**，后端启动时从前端文件"抄"一遍。
> 这解释了为什么两边商品数都是 267、id 都一样（`fa001`…）。
> ⚠️ 也意味着：**改前端 data.js 的价格，后端库不会自动跟着变**（要重启服务才重新灌，且 `initProducts` 只在"库里没有该商品"时才插）。

## 3. 吃透自检 5 问（能答就是吃透了）

| # | 问题 | 答案在哪 |
|---|---|---|
| 1 | 用户点「立即认养」，浏览器发出的第一个 HTTP 请求是什么？ | `POST http://localhost:3001/api/orders`，带 `Authorization: Bearer <token>`（`product-detail.html:950` → `js/api.js` → `server.js:303`） |
| 2 | **哪个页面的商品数据是过时的？为什么？** | `products.html` 列表页——用 `data.js` 本地常量（`:416`），不走接口；后端改了库存/价格它不跟着变 |
| 3 | 下单会改哪几张表？ | `orders`（插/更新）+ `products`（扣库存），共 2 张 |
| 4 | 取消订单的库存会恢复吗？ | 会（`server.js:438` `stock = stock + order.quantity`）；但 quantity 为负时会**反向污染** |
| 5 | 前端怎么拿到登录凭证？为什么 `js/api.js` 要单独封装一层？ | `localStorage` 里的 `token`；封装层统一给每个请求加 `Authorization` 头、统一抛错，业务页面不用各写一遍 |

## 4. 由"吃透"直接推出的改造清单（4 项）

| # | 改造项 | 为什么必须改 | 落在 D 几 | 对应真实 JD |
|---|---|---|---|---|
| **R1** | `quantity` 正整数校验 | 负数让库存虚增（实测复现 999 → 1004） | **D4** | 缺陷 16% |
| **R2** | 金额守恒：`price` 改数值列 + `total_price = 单价 × 数量` + **下单价格快照** | 金额不守恒 + 历史订单金额无法复现 | **D4** | 缺陷 16% |
| **R3** | 原子扣减：`UPDATE ... SET stock = stock-? WHERE id=? AND stock>=?` + 校验影响行数 + 事务 | 并发超卖：12 并发下 5 件库存卖出 12 单，stock=-7 | **D4** | 缺陷 16% / 性能 18% |
| **R4** | **`products.html` 列表页接后端**（`ProductAPI.list`） | 列表页与详情页价格/库存可能不一致 → 用户下单前后看到两个价 | **D8（可选）** | 全栈作品 / 数据一致性 |

> R4 是**可选加项**，主线的测试与重写不依赖它。但做完之后"列表页显示的价格 = 实际下单的价格"这条不变量才成立，
> 而且它正好是一个**能写进用例矩阵的数据一致性场景**。

## 5. 术语速查（第一次看这个项目会卡住的词）

| 词 | 在这个项目里指什么 |
|---|---|
| `认养` | 商品的品类（`cat='adopt'`），买的是"认养一棵树/一片海参"的名额，不是实物 |
| `zone` / `tagZone` | 首页的"专区"分区（mountain/sea/coast…），前端用来打标签和配色 |
| `farmer` | 合作社/农户，后端存成字符串，**没有 farmer 表** |
| `total_stock` / `stock` / `quantity` | 三个容易混：前两个是后端库存字段；`data.js` 里的 `quantity` 是**商品可售份数**（初始化时被当成初始库存灌进 `stock` 和 `total_stock`，见 `server.js:679`） |
| `pending` | 订单待付款状态。全系统只有 `pending` 和 `cancelled` 两个状态，**没有"已支付"** |
| `api.js` 的 6 个全局对象 | `AuthAPI / ProductAPI / OrderAPI / UserAPI / GrowthLogAPI / FavoriteAPI / FarmerFollowAPI`（`js/api.js:453-503`） |

> ⚠️ **`quantity` 一词两义**：`data.js` 里是商品可售份数；`POST /api/orders` 里是**下单数量**。
> 后端初始化时把前者灌进 `stock` 和 `total_stock`（`server.js:679`），很容易看串 → 这是我们测"库存守恒"时必须先确认语义的原因。
