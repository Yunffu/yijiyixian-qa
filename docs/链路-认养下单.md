## 0. 一句话结论（先记住这句）

> **当前的一季一鲜 = 一套"前端演示系统" + 一套"完整但完全没被使用的后端"。**
> 前后端共用同一份静态商品文件 `data.js`，但**前端一个后端接口都没调用**（除了地图页的 `/api/viz/stats`）；
> 后端那 24 个接口（登录/下单/订单/收藏/关注）**在前端里一次都没出现过**。

→ 这不是 bug，是我们**接下来 15 天的改造清单本身**（见 §4）。

## 1. 用户侧动作 → 代码落点（主链路）

### 1.1 浏览商品列表（`products.html`）

| 步 | 发生了什么 | 落点 |
|---|---|---|
| 1 | 打开 `products.html`，`<script src="data.js">` 把商品常量注入页面 | `products.html`（head） |
| 2 | `const mockProducts = PRODUCTS;` —— **前端直接用本地常量当数据源** | `products.html:416` |
| 3 | `getFiltered()` 按 region / zone / cat / 搜索词过滤 | `products.html:529` |
| 4 | `pickNine()` 每次取 9 个，`renderProducts()` 渲染卡片 | `products.html:557 / 713` |
| 5 | 卡片上的按钮文案是**「查看详情」**，点击跳 `product-detail.html?id=xxx` | `products.html:592-595` |

> 📌 文件里第 414 行有一句 `fetch('/api/products')`，但**上面第 416 行直接把数据源定死成了 `mockProducts`**，
> 并且注释写着「商品数据（来自 data.js）／**上线后替换为 fetch('/api/products')**」→
> **说明"接后端"是当初就知道、但没做的事。**

### 1.2 商品详情（`product-detail.html`）

| 步 | 发生了什么 | 落点 |
|---|---|---|
| 1 | 从 URL 取 `?id=`，从 `PRODUCTS` 里 find 出那一个商品 | `product-detail.html` |
| 2 | **没有任何 `fetch`** → 详情页也是纯前端数据 | 已 grep 确认 |
| 3 | 页面有"认养"入口，但**没有加入购物车 / 没有下单表单** | `product-detail.html` |

### 1.3 后端下单接口（`POST /api/orders`）—— **前端从不调用它**

这是全项目最关键的一段，`backend/server.js`：

| 步 | 发生了什么 | 落点 | ⚠️ 缺陷 |
|---|---|---|---|
| 1 | 鉴权：没有 `Authorization: Bearer <token>` 直接 401 | `server.js:303` → `authMiddleware` `server.js:33` | — |
| 2 | 取参 `product_id / quantity / receiver_name / receiver_phone / receiver_address` | `server.js:305` | **quantity 无正整数校验** |
| 3 | 收货三要素非空校验 | `server.js:310` | 手机号不校验格式 |
| 4 | `SELECT * FROM products WHERE id=?` 读商品 | `server.js:316` | — |
| 5 | `if (product.stock < quantity) 库存不足` | `server.js:329` | **读-判-写非原子**（无事务） |
| 6 | 查同用户同商品是否已有 `pending` 单 → 有则**累加数量** | `server.js:334` / `345` | 没有购物车，只能靠重复提交累加 |
| 7 | `INSERT INTO orders ...` 或 `UPDATE orders SET quantity=?` | `server.js:347` / `371` | — |
| 8 | `UPDATE products SET stock = stock - ?` | `server.js:377` / `381` | **未 await，且无事务 → 并发超卖** |
| 9 | 返回 `total_price: product.price`（**单价**，且是 TEXT） | `server.js:387` | **金额不守恒** |

### 1.4 取消订单（`PATCH /api/orders/:id/cancel`）

| 步 | 发生了什么 | 落点 |
|---|---|---|
| 1 | `SELECT * FROM orders WHERE id=? AND user_id=?` → **归属校验在这，横向越权走不通** | `server.js:420` |
| 2 | 状态必须为 `pending` | `server.js:430` |
| 3 | `UPDATE orders SET status='cancelled'` + `UPDATE products SET stock = stock + order.quantity` | `server.js:437-438` |

> 📌 缺陷 #1 的"回旋镖"：若订单 quantity 是 -5，取消时 `stock + (-5)` 会让库存**再减 5**。
> 即"下单 +5、取消 -5"双向污染。

### 1.5 数据从哪来（前后端共用同一个文件）

```
data.js:14   const PRODUCTS = [ ...267 条... ]
     │
     ├──[FE] products.html / product-detail.html / map.html  直接读这个常量
     │
     └──[BE] backend/server.js:639  initProducts()
             ├─ 正则从 data.js 抠出 `const PRODUCTS = [...]`   (server.js:659)
             ├─ `new Function(...)` eval 出对象数组              (server.js:665)
             └─ 逐条 INSERT 进 SQLite products 表             (server.js:675)
```

> **前后端是同一份数据的两个副本**，后端启动时从前端文件"抄"一遍。
> 这解释了为什么两边商品数都是 267、id 都一样（`fa001`…）。

## 3. 吃透自检 5 问（能答就是吃透了）

| # | 问题 | 答案在哪 |
|---|---|---|
| 1 | 用户点「查看详情」之后，浏览器发出了哪个 HTTP 请求？ | **没有**。纯前端跳转 `product-detail.html?id=xxx` |
| 2 | 前端商品数据从哪来？ | `data.js:14` 的 `PRODUCTS` 常量（267 条），不是接口 |
| 3 | 后端的商品数据从哪来？ | 启动时 `initProducts()` 从**同一个** `data.js` eval 出来灌库（`server.js:639`） |
| 4 | 下单会改哪几张表？ | `orders`（插/更新）+ `products`（扣库存），共 2 张 |
| 5 | 取消订单的库存会恢复吗？ | 会，`server.js:438` `stock = stock + order.quantity`；但 quantity 为负时会**反向污染** |

## 4. 由"吃透"直接推出的改造清单（4 项）

| # | 改造项 | 为什么必须改 | 落在 D 几 | 对应真实 JD |
|---|---|---|---|---|
| **R1** | `quantity` 正整数校验 | 负数让库存虚增（实测复现） | **D4** | 缺陷 16% |
| **R2** | 金额守恒：`price` 改数值列 + `total_price = 单价 × 数量` + **下单价格快照** | 金额不守恒 + 历史订单无法复现 | **D4** | 缺陷 16% |
| **R3** | 原子扣减：`UPDATE ... SET stock = stock-? WHERE id=? AND stock>=?` + 校验影响行数 + 事务 | 并发超卖，12 并发下 5 件库存卖出 12 单 | **D4** | 缺陷 16% / 性能 18% |
| **R4** | **前端接后端**：products 列表改真 `fetch('/api/products')` + 详情页加"立即认养"→ `POST /api/orders` | 让缺陷可从**真实用户路径**触发；也让"全栈"名副其实 | **D8（可选）** | 全栈作品 + 迁移性 |

> R4 是**可选加项**：主线的测试与重写不依赖它；但如果 D12–D14 有余量，做完 R4 的项目才是"能演示的产品"而不是"能演示的接口"。

## 5. 术语速查（第一次看这个项目会卡住的词）

| 词 | 在这个项目里指什么 |
|---|---|
| `认养` | 商品的品类（`cat='adopt'`），买的是"认养一棵树/一片海参"的名额，不是实物 |
| `zone` / `tagZone` | 首页的"专区"分区（mountain/sea/coast…），前端用来打标签和配色 |
| `farmer` | 合作社/农户，后端存成字符串，没有 farmer 表 |
| `total_stock` / `stock` / `quantity` | 三个容易混：前两个是后端库存字段，`quantity` 是**前端商品数据里的可售份数**（初始化时被当成初始库存灌进去，见 `server.js:679`） |
| `pending` | 订单待付款状态。全系统只有 `pending` 和 `cancelled` 两个状态，**没有"已支付"** |

> ⚠️ **`quantity` 一词两义**：`data.js` 里的 `quantity` 是商品可售份数；`POST /api/orders` 的 `quantity` 是**下单数量**。
> 后端初始化时把前者灌进 `stock` 和 `total_stock`（`server.js:679`），很容易看串 → 这是我们测"库存守恒"时必须先确认语义的原因。
